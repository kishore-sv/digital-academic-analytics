# Database Migrations (Alembic)

## Overview

**Alembic** is the sole schema migration tool for this project. All database schema changes must go through Alembic revision files — no raw SQL scripts, no manual DDL in production.

Alembic must be initialized **before the first SQLAlchemy model is written**. Retrofitting migrations after models exist is painful and error-prone.

## Setup Order

1. `uv add alembic` (future implementation task)
2. `uv run alembic init alembic` — creates `alembic/` directory and `alembic.ini`
3. Configure `alembic/env.py` to import `Base` from `app.core.database` and read `DATABASE_URL` from settings
4. Create first empty revision: `uv run alembic revision -m "initial"`
5. Write SQLAlchemy models with audit fields and indexes (see [database-constraints.md](database-constraints.md))
6. Autogenerate migration: `uv run alembic revision --autogenerate -m "add entities"`
7. Review autogenerated migration manually — Alembic does not catch everything
8. Apply: `uv run alembic upgrade head`

## Rules

- **No model is merged without a corresponding migration revision**
- Never edit a migration that has already been applied to a shared database — create a new revision instead
- Always review autogenerated migrations before applying; Alembic may miss index renames or constraint changes
- Migration files are committed to version control alongside model code

## Common Commands

```bash
# Apply all pending migrations
uv run alembic upgrade head

# Roll back one revision
uv run alembic downgrade -1

# Show current revision
uv run alembic current

# Show migration history
uv run alembic history

# Create a new autogenerated migration after model changes
uv run alembic revision --autogenerate -m "describe change"
```

## Relationship to Seed Data

Migrations create schema only. Seed/fixture data is loaded separately after migrations via a seed script (see [development-phases.md](development-phases.md) Phase 5).
